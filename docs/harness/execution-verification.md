# 执行与验证（Execution & Verification）

> 目标：让 Agent "做对事"——通过执行循环和强制验证确保任务被正确完成。

## 1. Agent Loop 执行循环

### 1.1 循环结构

```text
while 任务未完成:
    1. 观察（Observe）— 获取当前状态（git status、相关代码、需求 Spec）
    2. 推理（Think）— 分析状态，规划下一步
    3. 行动（Act）— 调用工具执行操作
    4. 验证（Verify）— 运行 pre-commit / pytest / lint 检查结果
    5. 更新（Update）— 更新任务状态
```

### 1.2 循环保护

| 保护机制 | 触发动作 |
|---------|---------|
| 最大修复次数 | 连续 3 次修复失败 → 暂停并请求人工介入 |
| 无进展检测 | 连续多次状态无变化 → 暂停 |
| 范围保护 | 修改超出任务范围的文件 → 撤销并提醒 |

## 2. 强制验证机制

### 2.1 预完成检查清单

Agent 在宣称任务完成前，必须逐项确认：

| 检查项 | 验证方式 | 跳过条件 |
|-------|---------|---------|
| 分层未被破坏 | `import-linter`（经 pre-commit） | 无后端代码变更 |
| 代码风格 / 类型通过 | `ruff` + `mypy`（经 pre-commit） | 无后端代码变更 |
| 后端测试通过 | `make test`（`pytest --reuse-db`） | 无后端逻辑变更 |
| 前端 lint 通过 | `npm run lint`（`src/pages`） | 无前端变更 |
| 前端文案已同步 | `zh.json` 与 `en.json` 同步维护 | 无用户可见文本变更 |
| 安全红线核查 | 对照 `docs/standards/security-bk-redlines.md` | 无（横切必查） |
| 对照任务 Spec | 逐条检查需求点 | 无 |
| 文档已同步更新 | 检查关联文档（架构 / 接口变更） | 无文档影响 |

> 前端未定义单元测试脚本，不得声称"测试已通过"；无法自动验证的交互须说明手工验证范围（见 `src/pages/AGENTS.md`）。

### 2.2 验证失败处理

- 验证失败 → 自动回到执行循环修复。
- 连续 3 次修复失败 → 暂停并请求人工介入。
- pre-commit 阻断的提交必须先修复，**禁止**使用 `--no-verify` 跳过。

## 3. 任务漂移检测

| 信号 | 含义 | 处理方式 |
|------|------|---------|
| 处理 Spec 以外的任务 | 任务漂移 | 回退到最近检查点 |
| 修改与任务无关的文件 | 范围蔓延 | 撤销变更并提醒（提交前核对 staged 范围） |
| 自主改变技术方案 / 分层 | 决策越权 | 暂停并请求确认 |
| 循环执行相同操作 | 陷入死循环 | 终止并报告 |

> 开始工作前先 `git status --short`，识别并保留用户已有改动；只修改任务必需的文件，不顺手格式化或重构无关代码。

## 4. 结果可观测性

### 4.1 执行日志

迭代研发流水线（tapd-story-pipeline / tapd-iteration-runner）在 `specs/{iteration}/` 下记录各需求的状态与成本数据；提交阶段汇总变更统计与 changelog。

### 4.2 运行时可观测性

| 维度 | 工具 | 访问方式 |
|------|------|---------|
| 健康检查 | `bkuser/monitoring/` | ping / healthz 接口 |
| 指标 | django-prometheus | `/metrics` |
| 链路追踪 | OpenTelemetry | settings 按需启用 |
| 异常 | Sentry | settings 按需启用 |

### 4.3 指标看板

| 指标 | 目标值 |
|------|-------|
| pre-commit 首次通过率 | 持续上升 |
| 分层违规数 | 0 |
| 需求交付验证通过率 | ≥ 90% |
